# 말랑 뽑기방, 강도 사다리 하나로 손맛을 묶자

말랑 뽑기방을 고도화하는 핵심은 새 효과를 더 얹는 일이 아니다. 이미 있는 연출(젤리 버튼, 등급별 캡슐, 신화·시크릿 3D 시퀀스, 합성 효과음)을 **하나의 "강도 사다리"**(일반 < 레어 < 에픽 < 전설 < 신화 < 시크릿)로 묶는 것이 핵심이다. 흔들림·파티클 수·햅틱·음 높이·예비동작 길이를 이 사다리 한 테이블(`data/rarity.ts`)에서 같은 비율로 꺼내 쓰면, 연출이 사건의 중요도를 그대로 전달하고 CLAUDE.md의 "수치 하드코딩 금지" 원칙과도 맞는다. 사운드는 지금 마스터 게인 하나에 기본값 컴프레서(threshold −24 dB, ratio 12)가 붙은 구조다. 이것을 음악/효과/UI 버스와 부드러운 컴프레서, 리미터로 바꾸고, iOS `'interrupted'` 상태에서 소리가 영영 멈추는 실제 버그부터 고쳐야 한다. UX에서 가장 큰 위험은 연출이 아니라 **저장 유실**이다. 주 유입 경로인 인스타그램 인앱 브라우저는 이동할 때 localStorage를 지울 수 있다는 보고가 있으므로, 저장 코드 내보내기/가져오기가 어떤 연출 개선보다 먼저다. 확률 표시는 코인을 유료로 살 수 없는 현재 구조라 법적 의무 대상이 아닐 가능성이 높다. 그래도 한국 법의 형식(캐릭터별 확률, 천장, 실질 확률)을 따라 두는 편이 싸고 안전하다. 그래픽은 필터 없이 그라데이션을 쌓는 젤리 재질, 부피를 보존하는 스쿼시&스트레치, 무작위 눈 깜빡임으로 "살아 있는 말랑이"를 만드는 쪽이 성능 대비 효과가 가장 크다. 아래에서 **출처가 있는 사실**은 인라인 링크로 표시했고, 링크 없이 "권장 시작값"이라고 쓴 수치는 노트의 추론이므로 실기기 플레이테스트로 조정해야 한다.

> 읽는 법: 링크가 붙은 문장 = 출처 확인된 사실(일부는 조사 당시 프록시 차단으로 검색 스니펫 기준). "권장 시작값" 또는 "추론"으로 표시한 숫자 = 업계 관행과 원칙에서 끌어낸 구현 출발점이며 1차 출처가 없다.

## 100ms 안에 반응하고 스프링으로 돌아오면 젤리가 된다

게임 필의 공개 근거는 개별 게임의 수치가 아니라 원칙과 플랫폼 토큰에 있다. 쿠키런·캔디크러시·포켓몬 GO의 버튼 스케일이나 ms 값을 공개한 1차 자료는 조사에서 찾지 못했다. 대신 Material 3의 duration 토큰은 **short 50/100/150/200ms, medium 250/300/350/400ms**이고 강조 easing은 `cubic-bezier(0.2, 0, 0, 1)`이다 ([design.md issue #47](https://github.com/google-labs-code/design.md/issues/47)). SwiftUI 기본 스프링은 response 0.55, damping 0.825다. response 0.3은 버튼 같은 작은 피드백에, 0.9는 모달 같은 극적 전환에 맞는다 ([Amos Gyamfi](https://medium.com/@amosgyamfi/learning-swiftui-spring-animations-the-basics-and-beyond-4fb032212487)). "Juice it or Lose it"(GDC Europe 2012)는 게임플레이를 그대로 두고 트윈·스케일·소리·파티클·흔들림·'눈 달기'만 얹어도 체감이 완전히 달라진다는 것을 보여 준 고전이다 ([GDC Vault](https://www.gdcvault.com/play/1016487/juice-it-or-lose)). 말랑 뽑기방은 이미 캐릭터에 눈이 달린 게임이니, 이 원칙을 UI 전체로 넓히면 된다.

**버튼(권장 시작값).** pointerdown에서 60–90ms 동안 아랫단을 0으로 누르고 `scale(0.97, 0.94)`, 젤리 느낌을 더 원하면 `scaleX(1.06) scaleY(0.90)`으로 찌그러뜨린다. pointerup에서는 `cubic-bezier(0.34, 1.56, 0.64, 1)`로 250–350ms 오버슈트하거나, CSS `linear()`로 감쇠 스프링 곡선을 굽는다. 효과음은 click이 아니라 **pointerdown**에 붙여야 50–150ms 늦게 느껴지지 않는다. 시각 반응 100ms 이내라는 목표는 M3 short2(100ms)와도 맞는다.

**화면 전환(권장 시작값).** 탭 간 이동은 페이지 루트에만 200–300ms 크로스페이드와 8–16px 슬라이드를 한 번 건다(섹션별 등장 애니메이션은 CLAUDE.md 금지 사항). 미니게임처럼 청크를 받는 전환은 말랑이 실루엣 "젤리 와이프"(400ms in → 대기 → 300ms out)로 가리되, 로딩이 150ms 안에 끝나면 건너뛴다. View Transitions API는 지원 브라우저에서만 쓰고, 미지원이면 즉시 전환한다. 지원 범위는 1차 출처로 확인하지 못했다.

**보상 연출.** 원신은 유성 색(파랑 3성/보라 4성/금 5성)으로 등급을 미리 알리고, 10연에서는 **묶음 최고 등급 하나만** 예고한다 ([HoYoLAB](https://www.hoyolab.com/article/634143)). 확정 보정이 발동하면 같은 5성 안에서도 다른 연출을 쓴다 ([Sportskeeda](https://sportskeeda.com/esports/genshin-impact-capturing-radiance-guide-boosted-5-star-drop-rate-characters-explained)). 말랑 뽑기방에 옮기면 두 가지다. 10연 머신 흔들림과 캡슐 색은 최고 등급 하나로만 결정하고, 천장으로 확정된 50번째 pull에는 별도 변형 연출(예: 캡슐 테두리 금박)을 붙일 수 있다. 코인 비행은 UI 좌표로 카운터 위치를 구해 코인 하나하나를 트윈하는 것이 표준 구현이다 ([dev.to coin-up](https://dev.to/chr15m/make-a-coin-up-game-animation-in-pure-css-and-javascript-3bj4)). 권장 시작값은 다음과 같다. 코인 **8–15개 상한**(금액을 개수로 표현하지 않음), 40–80px 방사 버스트 150ms, 50–80ms 간격으로 350–550ms 포물선 비행. 도착할 때마다 카운터를 `1→1.15→1`(120ms)로 튕기고 "틱" 음을 한 계단씩 올린다. 카운트업 길이는 `clamp(400, 300 + 150·log10(n), 1500)`ms에 `tabular-nums`, "+N" 팝업은 0→1.2→1(180ms) 뒤 24–40px 떠오르며 600–900ms 페이드한다. 10연은 최고 등급만 풀 연출하고 나머지는 50–80ms 스태거로 카드를 뒤집는다.

**히트스톱·흔들림·파티클.** 히트스톱은 강한 순간일수록 길게 두되 플레이어가 멈춤을 의식하기 직전에서 끊어야 한다 ([SmashWiki Hitlag](https://www.ssbwiki.com/Hitlag); [Blue Tengu](https://www.bluetengu.com/2014/12/12/art-of-screenshake-experiments/)). 사쿠라이 역시 "큰 순간에만 멈추라"고 조언한다 ([YouTube](https://www.youtube.com/watch?v=OdVkEOzdCPw)). 아래 사다리의 수치는 모두 권장 시작값이다.

| 등급 | 예비동작 추가 | 흔들림 maxOffset | 히트스톱 | DOM 파티클 | Android 진동 패턴 |
|---|---|---|---|---|---|
| 일반 | 0ms | 0 | 없음 | 3–6 | `10` |
| 레어 | +80ms | 0 | 33–50ms | 15–25 | `[20,50,40]` |
| 에픽 | +150ms | 4–6px | 50–80ms | 20–30 | `[20,50,40]` |
| 전설 | +300ms | 8–10px | 80–120ms | 30–60 (canvas) | `[30,60,30,60,80]` |
| 신화·시크릿 | 기존 epic 시퀀스 | 12–16px, 회전 ≤2° | 수축 뒤 150–250ms | three.js/canvas | 폭발 프레임에 `[0,120,60,40]` |

흔들림은 trauma(0–1) 모델로 `offset = max·trauma²`에 감쇠 약 1.5/s를 쓰고, 랜덤보다 Perlin 노이즈가 덜 어지럽다. `prefers-reduced-motion`이면 흔들림·파티클·오버슈트는 0으로 두고 색·소리·짧은 페이드만 남긴다. 콤보는 단계마다 음을 올리고 텍스트 스케일을 `1 + 0.08·n`(최대 1.6)으로 키운 뒤, 8–12단계에서 멈춘다(권장 시작값).

**햅틱은 선택적 향상일 뿐이다.** Android Chrome은 `navigator.vibrate`를 쓸 수 있지만 iOS Safari에는 Vibration API가 없다. iOS 17.4에 들어온 `<input type="checkbox" switch>`와 label 클릭 편법은 **iOS 26.5에서 프로그램적(untrusted) 클릭 경로가 막혔다**. 26.5 이후로는 사용자의 실제 탭이 투명 label에 닿을 때만 햅틱이 난다 ([npm ios-haptics](https://www.npmjs.com/package/ios-haptics); [PR #12](https://github.com/tijnjh/ios-haptics/pull/12)). 그래서 iOS에서는 뽑기 버튼이나 쓰다듬기처럼 **사용자가 누르는 그 순간**에만 햅틱을 줄 수 있고, 결과 공개처럼 시간이 지난 뒤의 진동은 불가능하다. 설정에 "진동 끄기"를 모션 설정과 별개로 둔다.

## 합성음은 이미 좋다 — 믹싱 구조와 iOS 복구가 약점이다

코드를 확인하면 `src/audio/sfx.ts`의 `ensureContext()`는 `state === 'suspended'`일 때만 `resume()`한다. 출력은 마스터 게인 0.5 하나에서 **기본 설정 그대로인 `DynamicsCompressorNode`** 로 곧장 나간다. 여기에 두 가지 구체적 문제가 있다.

첫째, iOS Safari는 앱 전환·탭 전환·화면 잠금 때 컨텍스트를 비표준 `'interrupted'` 상태로 바꾼다. `visibilitychange`에서 resume을 부르는 것만으로는 복구가 불안정하다. `'suspended'`만 검사하는 잠금 해제 코드가 인터럽트 뒤에 소리가 멈춘 채 남는 버그는 실제 프로젝트에서도 보고됐다 ([roadbook #937](https://github.com/alvarofranz/roadbook/issues/937); [Matt Montag](https://www.mattmontag.com/web/unlock-web-audio-in-safari-for-ios-and-macos)). 조건을 `state !== 'running'`으로 바꾸고, 전역 non-passive `pointerdown`/`touchend`/`keydown` 핸들러 안에서 동기적으로 `resume()`해야 한다. 둘째, Web Audio 컴프레서의 기본값은 **threshold −24 dB, knee 30, ratio 12, attack 3ms, release 250ms**다 ([MDN 미러](https://udn.realityripple.com/docs/Web/API/DynamicsCompressorNode/DynamicsCompressorNode)). 게임 마스터에 두기에는 지나치게 세서, 신화 폭발처럼 큰 소리가 날 때 나머지가 눌려 버린다.

**버스 구조(권장 시작값).** 목소리 → {uiBus 0.4–0.5, sfxBus 0.6–0.7, musicBus 0.15–0.2 + duckGain} → HPF(80–120Hz, Q 0.707) → 버스 컴프레서(threshold −18 dB, knee 6–10, ratio 3–4, attack 5–10ms, release 150–250ms) → 리미터(threshold −1 ~ −3 dB, knee 0, ratio 20, attack 1–3ms, release 50–100ms) → 마스터 볼륨 순서다. 휴대용 게임 라우드니스 기준은 콘솔(약 −24 LUFS)보다 큰 **약 −16 LUFS**이고, Sony의 모바일 목표는 −18 LUFS로 인용된다 ([VNDev Wiki](https://vndev.wiki/Guide:Balancing_a_Game's_Loudness); [Sony ASWG-R001](http://gameaudiopodcast.com/ASWG-R001.pdf)). 브라우저 안에 미터가 없으니 개발 스크립트에서 `OfflineAudioContext`로 30–60초 세션을 렌더링하고, JS BS.1770 구현으로 −16 LUFS / true peak ≤ −1 dBTP를 맞춘다. 개별 효과음은 마스터 전 −12 ~ −6 dBFS 피크로 두고, 이벤트 종류별 동시 발음 수를 제한한다(예: 코인 최대 6개, 가장 오래된 것부터 끊기).

**휴대폰 스피커에서 들리는 대역으로 옮긴다.** 폰 스피커는 대부분 200Hz 아래를 거의 못 내고, 측정상 Android 게임은 약 220Hz, iPhone 7 Plus는 약 400Hz부터 올라온다 ([Audiokinetic](https://www.audiokinetic.com/en/community/blog/loudness-and-frequency-response-on-popular-smart-phones/); [LANDR](https://blog.landr.com/make-bass-audible-phone-speakers/)). 그러면 현재 `epicImpact`(90→32Hz)와 `secretBoom`(62→22Hz) 사인파는 폰에서 거의 들리지 않고 컴프레서만 건드린다는 결론이 나온다(추론). 150–400Hz 배음 "쿵"(2배음 삼각파나 `WaveShaperNode` 포화)을 겹쳐야 폰에서도 무게가 전달된다. UI·보상음 기본음은 C5–C7(523–2093Hz), 젤리 몸통 소리는 250–600Hz + 노이즈에 두고, 4kHz를 넘는 지속음은 피한다. 스테레오는 ±0.2 이내로 두고 300Hz 아래는 가운데로 모은다.

**UI 사운드 패밀리.** 반복 피로는 이벤트당 변주 4–8개와 매번 바뀌는 피치·음량(±10–20%, ±3 dB)으로 줄이는 것이 관행이다 ([A Sound Effect](https://www.asoundeffect.com/game-audio-immersion/)). 연쇄에서 음을 올리면 연쇄의 길이가 강조된다 ([Game Developer](https://www.gamedeveloper.com/audio/the-power-of-pitch-shifting)). Stem Shift는 매치마다 반음씩 약 1.5옥타브까지 올린다 ([Stem Shift devlog](https://tessellum.itch.io/stemshift/devlog/1653666/let-there-be-sound)). 동물의 숲은 UI 동작마다 전용 소리를 두고 상황별 변형까지 만든다 ([Harper Ma](https://www.chuhanma.com/blog/animalcrossingsound)). 합성음이라면 권장 시작값은 이렇다. 탭·쓰다듬기에는 ±15–30 cents detune과 ±1.5 dB를 주고, 확인·코인음은 BGM과 조가 맞도록 정확한 음에 둔다. 콤보·코인 사다리는 반음 대신 **C장조 펜타토닉 계단**으로 8–10단계까지만 올리고, 600–800ms 동안 입력이 없으면 처음으로 되돌린다. 탭은 1.5–3kHz 15–40ms, 확인은 4도·5도 상행 2음(음당 80–150ms), 취소는 같은 음색의 하행, 오류는 300–500Hz "봉" 2회다. 어택은 2–5ms, UI는 250ms 미만, 보상은 600ms 미만. 쓰다듬기는 대역통과 노이즈에 20–40% 하강 글라이드를 섞고, 누른 속도에 컷오프를 연동한다. 코인음의 B5→E6 4도 사각파는 마리오 코인 레시피와 같다 ([Super Mario Wiki](https://www.mariowiki.com/Coin_(sound_effect))). 참고로 한 검색 요약에 있던 "B5=1012Hz, E6=758Hz"는 틀렸다. 평균율에서는 B5 ≈ 987.8Hz, E6 ≈ 1318.5Hz다.

**절차적 BGM.** 스케줄링은 Chris Wilson의 "두 개의 시계" 방식이 표준이다. JS 타이머가 약 25ms마다 돌면서 앞으로 약 100ms 안에 올 음을 `AudioContext.currentTime` 기준으로 미리 예약한다 ([web.dev](https://web.dev/articles/audio-scheduling); [IRCAM](https://ircam-ismm.github.io/webaudio-tutorials/scheduling/timing-and-scheduling.html)). 모바일에서는 메인 스레드가 밀리므로 예약 범위를 0.2–0.3초로 늘린다(권장). 코지 게임 음악은 60–100 BPM에 코드 변화를 적게 두고, 피아노·글로켄슈필·마림바·첼레스타·칼림바를 쓴다 ([Orchestral Tools](https://www.orchestraltools.com/tips-for-cozy-game-music)). 마림바 배음은 **1 : 3.92 : 9.24** ([Euphonics](https://euphonics.org/3-3-marimbas-and-xylophones/)), 종소리는 C:M 1:1.4 FM에 변조 지수를 빠르게 줄이는 Chowning 방식으로 만든다 ([Tonalux](https://tonalux.org/blog/fm-synthesis-bessel-functions-sideband-math)). 권장 시작값은 다음과 같다. 홈 88–96 BPM, 도감 72–80 BPM 뮤직박스, 만지기 64–72 BPM 칼림바, 미니게임 110–128 BPM. 뽑기 화면에는 루프 없이 패드나 드럼롤만 두고, 팡파르가 울릴 때는 음악을 10–15 dB 덕킹하거나 멈춘 뒤 결과 카드가 뜨고 1–1.5초에 걸쳐 되돌린다. 짧은 효과음에는 약 3 dB 덕킹(attack 30–50ms, release 300–500ms)을 건다. 화성은 4마디 I–V–vi–IV에 펜타토닉 멜로디, 시드 RNG(`lib/rng.ts`)로 4–8마디마다 리듬을 바꾸고, 화면이 바뀌면 다음 마디에서 1–2초 동안 등전력 크로스페이드한다. 저음은 C3(130Hz) 이상에 2·3배음을 더해 폰에서도 들리게 한다.

**모바일 정책.** iOS에서 Web Audio는 기본적으로 무음 스위치에 음소거되는 ambient 계열 세션을 쓴다. iOS 17 이후 Safari는 `navigator.audioSession.type = 'playback'`으로 무음 스위치를 무시할 수 있지만, 그러면 다른 앱의 음악이 멈춘다 ([W3C 설명서](https://github.com/w3c/audio-session/blob/main/explainer.md); [nattog.dev](https://nattog.dev/blog/web-audio-ios-unmute)). 인스타 DM으로 공공장소에서 들어오는 사용자가 많으니 기본값은 무음 스위치 존중과 사용자 음악 믹스로 두고, "무음 모드에서도 소리 켜기"는 설정 옵션으로만 제공하는 편이 맞다(추론). 인앱 WKWebView에서 이 API가 동작하는지는 확인하지 못했다. 배터리를 위해 `visibilitychange: hidden`, 30초 무음, 음소거 상태에서는 BGM 스케줄러를 멈추고 `ctx.suspend()`한다. 유휴 컨텍스트를 suspend해서 실제 배터리 소모를 고친 사례도 있다 ([element-web PR #29203](https://github.com/element-hq/element-web/pull/29203)). 설정에는 배경음악과 효과음 슬라이더를 따로 두고, 음악 기본값은 작게(약 −18 dB) 잡는다.

## 가장 큰 UX 위험은 연출이 아니라 사라지는 저장이다

**저장 안전.** 한 개발자는 인스타그램 인앱 브라우저가 이동할 때 localStorage를 지우고, sessionStorage에 이중으로 쓰면 누락의 87%를 잡았다고 보고했다. 단일 일화이니 수치는 참고만 한다 ([DEV](https://dev.to/forrestmiller/instagram-wipes-localstorage-on-navigation-heres-how-we-keep-multiplayer-sessions-alive-8e0)). WebView에서는 PWA 설치가 안 되고, iOS 홈 화면 앱은 Safari와 저장소가 분리되어 진행이 자동으로 넘어가지 않는다 ([MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)). 로그인이 없는 게임에서 사파리→홈 화면 앱으로 진행을 옮길 **유일한 경로는 저장 코드**다. 권장안은 다음과 같다. "저장 코드 복사"는 sanitize한 세이브를 압축 base64 + 체크섬, 2–4KB 이하로 만든다. "저장 코드 붙여넣기"는 기존 `sanitizeSave`와 `migrateSave`를 그대로 통과시킨다. 인앱 브라우저에서는 sessionStorage에도 미러링하고, 덮어쓰기 전에 `.bak` 백업을 남기며, 실제 브라우저에서는 첫 의미 있는 진행 뒤 `navigator.storage.persist()`를 요청한다. 인앱 브라우저 안내는 첫 뽑기 전에 막는 모달이 아니라 부드러운 배너로 띄운다.

**온보딩.** 약 1분 안에 핵심 재미에 닿아야 하고, 약 90초가 넘으면 상당수가 두 번째 세션에 돌아오지 않는다는 업계 경험칙이 있다 ([Playio](https://blog.playio.co/mobile-game-onboarding-retention)). 온보딩 화면은 3장 이하, 한 번에 한 메커닉, 건너뛰기 제공이 권장된다 ([Design Studio](https://www.designstudiouiux.com/blog/mobile-app-onboarding-best-practices/); [Game Developer](https://www.gamedeveloper.com/design/best-practices-for-a-successful-ftue-first-time-user-experience-)). 이 게임의 "아하" 순간은 미니게임이 아니라 **첫 캡슐**이다. 그래서 첫 흐름을 5탭·60초 이하로 설계한다(추론). 홈에 "첫 뽑기 선물" 코인이 보이고 → 강조된 뽑기 버튼 → 머신 → 결과에서 "파트너로 정하기" → "미니게임으로 코인 모으기" 한 줄 순서다. 일일 미션·세트·만지기·설치 카드는 첫 뽑기 뒤에 공개하고, 코치마크는 기능별 첫 방문에만 띄운다. 첫 뽑기를 레어 이상으로 보정한다면 확률표에 그 사실을 적는다. 목표치로 쓸 만한 벤치마크는 GameAnalytics 2025 기준 **D1 중앙값 22%, 상위 25%는 25–33%, D7 중앙값 3.4–3.9%, 상위 25%는 7–8%**다 ([GameAnalytics 2025](https://www.gameanalytics.com/reports/2025-mobile-gaming-benchmarks)). 웹 PWA 전용 벤치마크는 없으니 앱 수치를 근사치로 쓴다.

**비약탈적 리텐션.** Duolingo는 스트릭 프리즈 도입 뒤 이탈 위험군의 이탈이 21% 줄었다고 널리 인용되지만, 1차 발표는 찾지 못했다 ([Apptitude](https://apptitude.io/blog/how-duolingos-streak-mechanic-actually-works/)). 권장안은 다음과 같다. 출석은 끊겨도 초기화되지 않는 누적 7일 도장으로 하고, 7일째 보상을 뽑기 1회분 정도로 준다. 세트 진행("깊은 바다 세트까지 2마리")을 홈의 다음 목표 칩으로 올리고, 결과 화면마다 한 줄 넛지("코인 120개 더 모으면 한 번 뽑을 수 있어요")를 둔다. 만료 코인, 한정 확률업 타이머, 확률을 속이는 "아깝다" 연출은 쓰지 않는다. iOS 웹 푸시는 16.4 이상에서 홈 화면에 설치한 앱만 받을 수 있고, 사용자 제스처로 권한을 요청해야 한다 ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)). 인스타 유입 사용자 대부분에게는 닿지 않고 VAPID 서버 비용도 들기 때문에 후순위다.

**한국 확률 표시 규제.** 게임산업법 개정안은 **2024-03-22부터** 확률형 아이템의 종류와 확률을 게임 안, 홈페이지, 광고에 표시하도록 의무화했다 ([정책브리핑](https://www.korea.kr/news/policyNewsView.do?newsId=148924297&pWise=main&pWiseMain=F2)). **온전히 무상**으로 얻는 아이템은 제외되지만, 직간접적으로 살 수 있는 기본 재화로 사는 아이템은 유료로 본다 ([테크M](https://www.techm.kr/news/articleView.html?idxno=120476); [화우](https://www.hwawoo.com/newsletter/2024_02_20/240220_k_g.pdf)). 최근 3년 평균 매출 1억 원 이하 사업자도 면제된다 ([디일렉](https://www.thelec.kr/news/articleView.html?idxno=26046)). 시행 초기 몇 달에 **266개 게임**이 위반으로 적발됐다 ([Game World Observer](https://gameworldobserver.com/2024/07/08/266-games-violated-loot-box-rules-south-korea)). 이후 입증 책임이 사업자로 넘어갔고, 최대 3배 징벌적 손해배상이 도입됐다 ([Chambers](https://practiceguides.chambers.com/practice-guides/gaming-law-2025/south-korea)). 애플(2017)과 구글(2019)도 구매 전 확률 공개를 요구한다 ([Fenwick](https://www.fenwick.com/insights/publications/apple-now-requires-disclosure-of-loot-box-odds)). 코인을 플레이로만 얻는 지금은 의무 대상이 아닐 가능성이 높다(법률 자문 아님). 하지만 **코인 판매나 유료 보너스를 하나라도 추가하는 순간 캡슐 전체가 대상이 된다.** 그래서 지금부터 법의 형식을 맞춰 두는 것이 합리적이다. 뽑기 버튼 옆에 확률표 링크를 두고, 등급별 확률과 캐릭터별 확률(예: 시크릿 0.05% ÷ 3 ≈ 0.0167%), 천장 문장과 현재 카운터("확정까지 12번 남았어요"), 실질 전설 이상 약 4.2%, 10연 보장, 반짝 1% 독립, 중복 환급, 합계 100%, 최종 수정일을 표시한다. 최근 뽑기 기록도 보여 준다. 시행령 별표 3의2 원문과 해설서의 천장 표기·소수점 규정은 확인하지 못했다.

**상태 화면과 성능.** 빈 도감은 "?" 실루엣 캡슐 선반에 뽑기 버튼 하나, 코인이 부족하면 죽은 버튼 대신 "코인 40개가 더 필요해요" + 미니게임 링크, 300ms 미만 로딩에는 스피너 없음, 오프라인이면 "게임은 계속할 수 있어요" 토스트를 띄운다(권장). 성능 목표는 Core Web Vitals "좋음" 기준인 75퍼센타일 **INP ≤ 200ms, LCP ≤ 2.5s, CLS ≤ 0.1**이다 ([web.dev](https://web.dev/articles/vitals)). 뽑기 버튼은 100ms 안에 반응해야 하므로, 스토어 쓰기와 persist는 다음 프레임으로 미루고 첫 화면 JS는 gzip 150–200KB 이하를 목표로 한다(권장). 미니게임 중에는 동기식 localStorage 쓰기를 스로틀링한다.

**접근성.** Game Accessibility Guidelines 기본 단계는 색만으로 정보를 전달하지 말라고 한다. 가장 많이 나오는 불만은 조작 재배치, 글자 크기, 색각 이상, 자막이다 ([GAG Basic](https://gameaccessibilityguidelines.com/basic/)). 프로젝트는 이미 색+아이콘+텍스트 원칙을 지키고 있다. 추가할 것은 다음과 같다(권장). 모든 소리 신호에 시각 대응물을 둔다. 주요 버튼을 화면 아래 40%(엄지 영역)에 배치한다. 미니게임에 일시정지와 쉬운 모드를 둔다. 시크릿 초신성의 **한 프레임 색 반전**은 움직임 줄이기에서 끄고, 모션이 허용된 상태에서도 초당 3회 이하 섬광 규칙(WCAG 2.3.1)을 지킨다.

## 필터 없이 층을 쌓으면 싸고 맛있는 젤리가 나온다

**카와이 얼굴.** 귀여움은 큰 머리, 크고 낮게 자리한 눈, 작은 입, 통통한 볼 같은 "베이비 스키마"에서 나온다. 이런 특징이 많을수록 더 귀엽게 평가되고 보살핌 동기도 커진다 ([PubMed](https://pubmed.ncbi.nlm.nih.gov/22267884/)). 이 반응은 보상 회로와 연결되고 문화에 걸쳐 보편적이다 ([PNAS](https://www.pnas.org/doi/10.1073/pnas.0811620106)). 카와이 튜토리얼들은 눈을 얼굴 중간쯤 또는 그 아래에 넓게 벌리고, 입은 눈 높이 가까이 두며, "보통 크기로 보이면 2배로 키우라"고 한다 ([Creative Bloq](https://www.creativebloq.com/character-design/10-tips-kawaii-character-design-514833); [Tatyana Deniz](https://tatyanadeniz.com/kawaii-faces/)). 몰랑이는 주먹밥 같은 타원 하나에 웃을 때 작은 아치 눈 두 개와 세로선 입이면 끝이다 ([Tatyana Deniz: Molang](https://tatyanadeniz.com/how-to-draw-molang/)). 권장 시작값(몸 높이 H, 폭 W 기준)은 다음과 같다. 눈 중심은 위에서 55–62%, 눈 간격은 W의 34–42%, 눈 반지름은 H의 6–8%에 반지름 35–40%의 하이라이트를 둔다. 입 폭은 W의 6–10%, 볼터치는 W의 12×7% 타원에 불투명도 35–55%로 넣고, 작은 크기에서는 사선 해칭이 더 잘 읽힌다. 48px 도감 타일에서는 실루엣, 눈 두 개, 볼터치만 남기고 종을 귀·꼬리·모자로 구분한다. 표정 세트(기본·^^·깜빡·놀람·졸림)는 모든 캐릭터가 함께 쓴다.

**젤리 재질.** 캔디크러시의 원칙은 "2D는 최대한 평평하게, 3D는 터무니없이 맛있어 보이게"다 ([PocketGamer.biz](https://www.pocketgamer.biz/the-secret-ingredients-behind-the-art-of-candy-crush-saga/)). 이 원칙은 CLAUDE.md의 "패널은 평평한 외곽선, 눌리는 것만 두꺼운 아랫단"과 정확히 겹친다. 성능 쪽 근거도 분명하다. SVG 필터 원시 요소를 4개 넘게 이으면 모바일이 크게 느려지고, 필터 하나 때문에 iPhone SE에서 60fps가 12fps로 떨어진 보고가 있다 ([svg2png.org](https://www.svg2png.org/blog/svg-filter-effects-guide)). CSS blur는 10px를 넘으면 프레임이 떨어진다 ([generalistprogrammer](https://generalistprogrammer.com/tutorials/css-filters-complete-guide)). 따라서 말랑이 몸은 **필터 0개, 그라데이션 7층**으로 만든다(권장 시작값, 몸 크기 S 기준). 첫째, 바닥 그림자는 폭 80%·높이 10% 타원에 잉크 12–18%를 쓴다. 둘째, 몸통은 초점 (35%, 25%) 방사형 그라데이션으로, 0%는 OKLCH로 +18% 밝게, 55%는 기본색, 100%는 −12% 어둡게 하고 채도를 살짝 올린다. 셋째, 아래 안쪽 그늘은 55%부터 25% 불투명도로 넣는다. 넷째, 아래쪽 70% 지점에 더 밝고 따뜻한 산란광을 30–40%로 깐다. 다섯째, 흰 반사광 22×12% 타원을 −25° 회전해 (30%, 22%)에 불투명도 85–95%로 선명하게 넣는다. 여섯째, 좌상단 가장자리 안쪽 5%에 두께 2–3%의 림 하이라이트를 긋는다. 일곱째, 같은 색상을 어둡게 한 외곽선을 표시 크기의 3–4% 두께로 두른다(96px에서 3px, 48px에서 2px). 신화 캡슐 뒤의 빛처럼 번짐이 꼭 필요하면 미리 흐린 방사형 그라데이션을 쓰고, `stdDeviation`은 절대 애니메이션하지 않는다.

**스쿼시&스트레치.** 한 축이 늘면 다른 축이 줄어 부피가 보존되어야 한다(예: scaleX 1.3 ↔ scaleY 0.7) ([CodeFronts](https://codefronts.com/motion/css-bounce-animation/physics-ball-squash-stretch/)). 스프링은 이런 탄성 표현에 잘 맞는다 ([Josh W. Comeau](https://www.joshwcomeau.com/animation/squash-and-stretch/)). 기본값은 Framer Motion stiffness 100 / damping 10 / mass 1, SwiftUI 출발점은 170 / 15다 ([Maxime Heckel](https://blog.maximeheckel.com/posts/the-physics-behind-spring-animations/)). 눈 깜빡임은 약 100–150ms 걸리고 간격은 무작위로 두는 것이 자연스럽다 ([Wikipedia: Blinking](https://en.wikipedia.org/wiki/Blinking)). 권장 시작값은 이렇다. 숨쉬기는 scaleY 1→1.03, scaleX = 1/scaleY, 주기 2.4–3.2초, `transform-origin: 50% 100%`에 캐릭터별 위상을 무작위로 준다. 탭하면 scaleY 0.82 / scaleX 1.18에서 stiffness 300–500, damping 10–14 스프링으로 0.5–0.7초 동안 2–3번 출렁인다. 버튼보다 damping을 낮춰야 떡처럼 느껴진다. 착지는 공중에서 scaleY 1.15, 접촉 순간 0.8로 400–600ms. 깜빡임은 닫기 60ms, 유지 40ms, 열기 80ms에 간격 2.5–6초 균등 무작위, 이중 깜빡임 확률 10–15%다. 눈과 하이라이트를 몸보다 1–2프레임 늦게 따라오게 하면 속이 출렁이는 느낌이 난다. `touch/physics.ts`의 스프링 모듈을 버튼과 결과 카드에도 재사용할 수 있다. 움직임 줄이기에서는 숨쉬기와 튕김을 끄고 정지 포즈만 남긴다.

**팔레트와 대비.** WCAG AA는 일반 텍스트 4.5:1, 큰 텍스트(24px 또는 18.66px 굵게 이상) 3:1을 요구한다 ([WebAIM](https://webaim.org/articles/contrast/)). 파스텔 위의 흰 글자는 대부분 통과하지 못한다 ([WebAbility](https://www.webability.io/blog/color-contrast-for-accessibility)). 따라서 본문은 파스텔 위에 잉크 `#2b2233`으로 쓰고, 풍선 제목은 큰 글자에만 쓰되 대비를 **3px 이상 잉크 외곽선**이 책임지게 한다. 구현은 `-webkit-text-stroke: 0.14em var(--ink); paint-order: stroke fill; text-shadow: 0 0.08em 0 var(--ink)`이고, `paint-order`는 이제 주요 엔진 모두에서 지원된다 ([MDN](https://developer.mozilla.org/docs/Web/CSS/paint-order)). 등급 색은 Diablo·WoW 관례인 회색/흰색→초록→파랑→보라→주황을 따르고 ([Wikipedia: Loot](https://en.wikipedia.org/wiki/Loot_(video_games))), 색각 안전 팔레트 Okabe-Ito(#56B4E9, #CC79A7, #E69F00, #D55E00)를 기준점으로 삼을 수 있다 ([SciFig](https://scifig.ai/blog/okabe-ito-color-palette-hex-codes)). 파랑↔보라와 주황↔빨강은 색각 이상에서 헷갈리기 쉬운 쌍이다. 그래서 등급마다 **명도를 한 단계씩 확실히 다르게** 하고, 등급별 아이콘 모양(원·마름모·별·왕관·불꽃·반짝이)과 캡슐 줄무늬 패턴을 따로 준다(추론). 파스텔은 OKLCH L 0.80–0.90, C 0.08–0.14에 둬야 햇빛 아래 OLED에서도 회색으로 죽지 않는다(추론). 실제 토큰 값의 대비비는 계산하지 않았으니 WebAIM 검사기로 확인해야 한다. 장식은 스프링클 SVG 데이터 URI 타일(120px, 사각형 8–12개), 깅엄 이중 `repeating-linear-gradient`(16px), 차양 줄무늬(24px)처럼 한 번 그리고 끝나는 배경으로 만든다(외부 파일 금지 규칙 준수).

**렌더링 예산.** 컴포지터만으로 처리되는 속성은 `transform`과 `opacity`뿐이다. `will-change`는 레이어마다 GPU 메모리를 쓰므로 아껴야 한다 ([web.dev](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count)). three.js는 DPR을 2로 제한하는 것만으로 모바일 프레임이 두 배가 될 수 있다. 모바일 draw call은 약 100개 이하, 후처리는 절반 해상도로 돌리고, 그림자는 끄고, 텍스처는 512² 이하로 둔다 ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips); [Codrops](https://tympanus.net/codrops/2025/02/11/building-efficient-three-js-scenes-optimize-performance-while-maintaining-quality/)). 브라우저는 살아 있는 WebGL 컨텍스트를 약 8–16개로 제한하므로 `forceContextLoss()`와 `dispose()`를 함께 호출해야 한다 ([three.js PR #17588](https://github.com/mrdoob/three.js/pull/17588)). 현재 3D 연출 정책(지연 청크, 1.5초 폴백, 언마운트 시 해제)은 이미 이 권고와 맞는다. 추가 권장값은 다음과 같다. 에픽 씬은 DPR ≤ 2(첫 프레임이 20ms를 넘으면 1.5), draw call ≤ 50, bloom 절반 해상도·mip ≤ 5, 입자는 `Points`/`InstancedMesh` 하나로 처리한다. 2D에서는 움직이는 조각이 50개를 넘으면 canvas로 옮기고, 미리 그린 스프라이트를 `drawImage`로 찍는다. 프레임 시간이 여러 프레임 연속 20ms를 넘거나 `hardwareConcurrency ≤ 4`이면 파티클을 절반으로 줄인다. 도감은 `content-visibility: auto`와 IntersectionObserver로 동시에 움직이는 그룹을 20–30개 이하로 제한한다.

## 결론

이 조사가 바꾼 관점은 이렇다. "연출을 더 화려하게"라는 질문의 답은 대부분 이미 코드 안에 있고, 부족한 것은 **일관된 비례**와 **실패하지 않는 기반**이다. 신화·시크릿 연출은 이미 업계 수준인데, 그 폭발음의 주파수는 폰 스피커가 내지 못하는 대역에 있다. 소리를 되살리는 코드는 iOS 인터럽트 한 번에 멈추고, 수집의 결과물인 세이브는 주 유입 경로에서 지워질 수 있다. 그래서 가장 높은 투자 대비 효과는 한 줄짜리 오디오 수정, 믹싱 체인, 저장 코드라는 "보이지 않는 고도화"에서 나오고, 그 위에 강도 사다리 한 장이 모든 등급 연출을 묶는다.

불확실한 부분도 분명히 적어 둔다. 버튼·코인·콤보의 구체 수치는 어떤 게임의 공개 자료도 아닌 추론이라 실기기(특히 저가 Android와 인스타 인앱 브라우저) A/B 테스트가 필요하다. iOS 햅틱 우회와 인앱 WKWebView의 Audio Session 지원은 언제 바뀔지 모른다. 확률 표시 의무는 **코인을 파는 순간** 켜지는 스위치이므로, 수익화를 검토한다면 표시 체계를 먼저 법 형식에 맞춰 두는 것이 가장 싼 보험이다.
